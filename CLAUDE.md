# Founder Signal System, MVP

Context for whoever (or whichever Claude Code session) picks this up next. This file exists because the project was built in a chat session that Claude Code cannot see; everything it needs to know is written down here instead of assumed.

## What this is

A prototype dashboard for Motive Ventures (a fintech VC) that demonstrates how founder-quality scores (an existing 8-dimension interview framework already in use at the firm), founder intangibles ("why we believed"), and company outcomes (did the company graduate to its next round, MOIC) could be combined into an analytics layer. It is the MVP version of a larger plan (see "Origin and larger plan" below). Nothing here talks to Affinity, Notion or Box at runtime; it is fully self-contained and offline after the one-time data pull described below.

## Everything here is fabricated, read this before changing anything

`data/portfolio_roster.json` (51 "invested" companies: names, fund, vertical, current stage) used to be pulled from a real Affinity CRM export. As of this pass, it has been fully replaced with fabricated equivalents, fictional names in the same style as the passed-company list, fictional fund labels (Fund I / Fund II / Fund III / Legacy Fund), the same fictional-fintech verticals and stages. Every other field (`status`, `taxonomy`, `series`, `list_created_at`, `followon_entry`) was preserved exactly as it was, so the entire rest of the simulation, every score, lift, and outcome, regenerates numerically identical to before; only identity fields changed.

Synthetic, generated by `data/generate_synthetic.py` (seed 33, deterministic): every founder score, every intangible word or sentence, every rater, every outcome (graduated or not, MOIC marks, headcount), and all 68 "passed" companies (fictional names, invented to look like plausible fintech startups). No real founder, partner or rater name appears anywhere; raters are "Rater A" through "Rater F". Nothing in this repository is derived from any real company, fund, or CRM record.

The synthetic generator deliberately builds in patterns so the dashboard has something real to show: two dimensions (Ceiling, Talent magnetism) are constructed to predict graduation strongly; one dimension (Customer obsession) is constructed to be over-weighted by the fake decision process but to predict weakly; the invested population is constructed to have very little variance on Ceiling (because in the story, the firm already selects on it), which is what produces the "selection gap" visible in the dimension lift chart. If you regenerate with a different seed, the same structural patterns persist but are noisier at this sample size (119 founders, ~85 with resolved outcomes). SEED=33 was chosen from a sweep of 60 seeds specifically because the patterns are legible at that seed; see the sweep logic described in conversation, not currently saved as a script (a `sweep.py` reproducing it would be a reasonable thing to add if seed selection needs to be redone).

## Origin and larger plan

This MVP implements pieces of a larger plan that exists as a Notion page (not in this repo): "Founder Signal System: Build Plan (Agent 3 + Intangibles Layer)", drafted during the same session, describing how to turn Motive's existing "Team Interviewing Framework" (8 founder dimensions, a Pre-Screening Scorecard, and an internal Founder Radar tool) plus Affinity plus Box valuation data into a real, persisted analytics system. Key ideas from that plan carried into this MVP:
- Never average the 8 dimension scores; a single low score (a "veto") or high score (a "spike") matters more than a mean.
- Track founders you passed on, not just founders you invested in, because without them you cannot tell which traits actually predict success versus which traits you simply select for.
- "Graduation" (raised the next priced up-round within a stage-specific window: 18 months from Pre-Seed, 24 from Seed, 30 from Series A) is the primary near-term success label, because it is observable for both invested and passed companies. MOIC is the long-run label but only exists for invested companies and takes years to resolve.
- Intangibles ("three words", a lean-in sentence, a worry sentence) are a distinct data source from the 8 structured scores, meant to capture gut-level conviction that the structured framework might miss.

If asked to build the real (non-synthetic) version, the work is: create Notion databases for Founder Assessments and Company Outcomes, backfill Company Outcomes from Motive's quarterly Valuation Committee memos in Box (which contain marked Gross MOIC per company per quarter back to 2023), and point this same analytics layer at that real data instead of `data/data.js`. The analytics layer (`app/analytics.js`) is written to be data-source agnostic: anything producing the JSON schema in `SPEC.md` section 2 will work.

## Layout

```
SPEC.md                       full schema, generation rules, and analytics definitions (read this for any deep question)
README.md                     user-facing quickstart and section-by-section explanation of the dashboard
data/portfolio_roster.json    fabricated roster (was pulled from Affinity, now fully fictional, see above)
data/generate_synthetic.py    the synthetic data generator, stdlib Python only, deterministic
data/data.js, data.json       generated output (data.js is `window.FSS_DATA = {...}`, loaded by the app)
app/analytics.js              pure functions, no DOM, computes every metric shown on the dashboard
app/app.js                    all rendering, filters, the sortable founder explorer, the assessment form
app/index.html, app/styles.css
tests/test_analytics.js       node test, 18 groups / ~167 checks, validates data invariants and analytics correctness
tests/fixture.js, make_fixture.js   a small 6-company fixture used to test analytics before/independent of real data
tests/smoke_app.js            optional headless DOM render test (needs `jsdom`, not currently installed in this repo; install with `npm install jsdom` if you want it)
build/build_dist.py           inlines styles.css, data.js, analytics.js, app.js into one file
dist/founder-signal-mvp.html  the single-file build, this is what gets shared/opened in a browser
```

## How to work on this

```bash
# after changing generate_synthetic.py:
python3 data/generate_synthetic.py      # rewrites data/data.js and data/data.json

# after changing analytics.js or app.js, or regenerating data:
node tests/test_analytics.js            # must show "18 of 18 groups passed" before shipping a change

# after any change to app/ or data/:
python3 build/build_dist.py             # rebuilds dist/founder-signal-mvp.html, open this file to look at it
```

There is no build step for `app/index.html` itself; it can be opened directly in a browser (it loads `../data/data.js` relative to itself) for faster iteration than rebuilding `dist/` every time.

## Redesign pass (post-MVP), read this before restructuring the dashboard again

After the first MVP session, a self-critique (using the `coding-agent-critic` and `plain-language-reviser` lenses) found that the original 12-section dashboard had drifted from the actual question it was built to answer ("which founder dimensions predict success") into a scope-crept tour of every analysis that seemed adjacent, with statistician-facing language (raw "95% CI", "Selection gap" as a bare header) leading instead of a plain-language read. The fix, done in this pass:
- Added a "ground truth read" section at the very top (`app/index.html#sec-headline`, rendered by `renderHeadline` in `app/app.js`), built on two new pure functions in `app/analytics.js`: `dimensionDecisionLift` (does a high score predict getting invested at all, not just graduating) and `topInsights` (compares that against the existing graduation `dimensionLift` to surface "predictive" dimensions and dimensions the firm leans on that do not predict, i.e. "over-weighted"). See the README's "The two lift questions" section for the exact logic and thresholds.
- Collapsed the six exploratory/QA sections (persona by vertical, stage 1 to 2, intangibles, MOIC, rater calibration, data completeness) behind a single `<details id="supporting-detail">`, closed by default. They render lazily on first open (a `toggle` listener in `app.js`) so their charts get real width instead of laying out inside a zero-width closed `<details>`.
- Rewrote the Dimension lift table to lead with a plain "Read" column (Strong/Some/None/Reversed) right after the dimension name, with the raw lift and its CI combined into one secondary column instead of two, and moved the numbering so Population summary through Decision quality are 1 to 4 (the core, always-visible flow), Founder explorer and New assessment are 5 and 6, and the collapsed six have no numbers (they are detail, not part of the primary narrative).
- The original, pre-redesign single-file build was kept at `dist/founder-signal-mvp-approved-v1.html` for side-by-side comparison. The redesign was confirmed as the version worth keeping over many subsequent iterations, and that file was deleted during the pre-publish data fabrication pass (it still had the real, pre-fabrication portfolio data baked in). Unlike most deletions, it is not recoverable from git history either: as part of the same pre-publish pass, all prior commits (including the one this file came from) were squashed into a single fresh commit and the old history was garbage-collected, specifically because those commits still held the real, pre-fabrication data. If you need the pre-redesign version again, it would need to be rebuilt from scratch, not recovered.
- `liftRowsFromUnits` in `analytics.js` was generalized to take an optional `outcomeOf` accessor (defaults to graduation) so the new decision-lift calculation could reuse the exact same lift/CI math instead of duplicating it. `dimensionLift` and `vetoSpike` are unaffected; the 18/18 test suite still passes after this change.

## Data fabrication pass (pre-publish), read this before touching the roster or FUND_MAP

The user asked to fully fabricate the last real data in this repo so it would be safe to publish (originally to git). Before this pass, `data/portfolio_roster.json` held 51 real portfolio company names/domains/Affinity IDs, and `FUND_MAP` in `generate_synthetic.py` mapped Affinity status strings to Motive's actual fund names. Both are now fictional:
- The roster's `name`, `domain` and `affinity_entity_id` were replaced with fabricated equivalents, in the same style as the existing `PASSED_NAMES` list. Every other field (`status`, `taxonomy`, `series`, `list_created_at`, `followon_entry`) was left untouched on purpose, so the RNG stream in `generate_synthetic.py` consumes identically and every downstream number (lift, MOIC, outcomes) regenerates byte-for-bit unchanged. Verified directly: all 8 dimension lift values matched pre-fabrication numbers exactly after regenerating.
- `FUND_MAP`'s display values changed from the real fund names to the fictional Fund I/Fund II/Fund III/Legacy Fund. This required also fixing three places in `generate_synthetic.py` that compared `c["fund"] == "Realised"` as a literal string (the "force graduate, status realised" rule for that fund), those were still checking the old label and silently stopped firing until caught by a test failure and fixed to check `"Legacy Fund"` instead. If you ever rename FUND_MAP's values again, grep for `c["fund"] ==` first.
- The roster's internal `status` values (the Affinity list-status strings the whole thing keys off) were also fictionalized to "Portfolio Fund1/Fund2/Fund3" (`"Realised"` was left alone, it's a generic word, not a fund-specific codename). `FUND_MAP`'s keys were renamed to match. Don't just rename `FUND_MAP`'s values and call it done, the roster's `status` field is itself an identifiable internal code if left as the original real codename, even after its display label is fabricated.
- `app/app.js`'s `FUNDS` constant (the New assessment form's fund dropdown) and `tests/make_fixture.js` / `tests/fixture.js` (the standalone 6-company test fixture) were updated to match, so no real fund name is reachable anywhere in the app or test suite.
- Every doc claiming "real, from Affinity" (README, this file, SPEC.md, the in-app synthetic-data banner) was rewritten to state plainly that everything is fabricated. If you regenerate the roster again later, update those claims again too, they're easy to miss since they don't fail a test if they go stale.

## Known rough edges, worth fixing next

- `tests/smoke_app.js` needs `jsdom`, which was installed to a scratch npm prefix during the build session (`/tmp/smoke/node_modules`) rather than into this project; running `node tests/smoke_app.js` here will fail with "Cannot find module 'jsdom'" until you `npm install jsdom` inside this project folder.
- The seed sweep used to pick SEED=33 was done inline in a shell one-liner during the build session and was not saved as a script. If you need to re-tune the synthetic data's signal strength, you'll want to write that sweep logic back into a proper script rather than repeating it by hand.
- Only the CEO of each company is scored in this MVP (co-founders exist in `data.js` with an archetype but no assessments). This was a deliberate scope cut, not an oversight; `tests/test_analytics.js` checks CEO-only coverage explicitly. If the real system should score all founders, both the generator and the test need updating together.
- The intangibles word banks (`HIGH_WORDS` / `LOW_WORDS` in the generator) are mixed 70/30 by design (a "high quality" founder gets a low-bank word about 30% of the time and vice versa), so word frequency alone will show overlap between graduated and non-graduated founders in the dashboard. This is intentional realism, not a bug: see the "Words aspect" discussion in the session for why.
- `dist/founder-signal-mvp.html` is a generated artifact (from `build_dist.py`) and will go stale if `app/` or `data/` change without a rebuild. Consider whether it belongs in version control at all, or should be gitignored and rebuilt on demand; it is currently committed because the user wanted a single shareable file on hand.

## Conventions already in use, keep following them

No em dashes anywhere (data, code comments, or UI text); use commas or periods instead. Sentence case in all UI text, no title case, no exclamation points. No real person names anywhere, ever, including in code comments or test fixtures; use "Rater A" through "Rater F" or role-based labels like "CEO, Nelly". Every rate shown in the UI must show its underlying k/n counts, never a bare percentage. Flat design, 0.5px borders, no gradients or shadows, colors defined in `app/styles.css` as CSS variables (`--blue`, `--gray`, plus semantic green/amber/red used only with a text label).
